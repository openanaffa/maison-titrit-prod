## Design

### 1. Customer 360 detail page — `/makteb/customers/[id]`
- **Identity card**: name, email + verified badge (`emailVerified`), phone
  (digits-normalized, labelled unverified — no phone verification exists),
  account created date, role.
- **Order history**: orders by `userId` (account orders) **plus** guest
  orders matched by digits-normalized phone or exact email — rendered as
  "matched (unverified)" and never merged into the account record.
  Identity matching rule: **no merge on an unverified identifier**
  (acceptance criterion) — matches are a display association only.
- **Interactions**: the orders' `OrderNotification` rows (channel/event/
  status/attempts/lastError) as the activity timeline. Existing historical
  WhatsApp notification rows may be displayed but are not sent or retried;
  customer-initiated `wa.me` links remain outside this notification ledger.
- **Notes**: staff notes with author + timestamp; add/remove behind
  `customers:write`.

### 2. Segmentation primitives on the list page (no third-party CRM)
Server-side filters via `searchParams`: search (name/email/phone),
segments: `has-orders`, `guest-linked` (guest orders match this
customer's identifiers), `email-verified`, `marketing-consent`. Order
counts per customer included in the same repo pass.

### 3. Schema (both Prisma schemas lockstep + tracked SQL migration)
- `User.marketingConsent String?` — null = unknown, `OPTED_IN` /
  `OPTED_OUT`. Staff can record a customer's verbal consent (audited);
  storefront preference sync is out of scope until #125.
- `CustomerNote { id, userId, authorId (User), body, createdAt }`.
- `CustomerAuditEvent { id, userId?, actorId (User), action, detail?,
  createdAt }` — actions: `VIEW_CUSTOMER`, `NOTE_ADDED`, `NOTE_REMOVED`,
  `CONSENT_CHANGED`.
- `supabase/migrations/20261127000000_customer_360.sql` (idempotent DDL)
  + RLS lockdown migration for both new tables: anon revoked, staff-only
  read (per learning: tracked migrations + unique version prefixes).
- Live DB synced in the same change.

### 4. Privacy-aware access + audit
- Page + APIs: `customers:read` (FOUNDER/ADMIN/MANAGER/MARKETER — all
  staff); mutations (`customers:write`) = FOUNDER/ADMIN/DEVELOPER.
- Every render of the customer 360 page writes a `VIEW_CUSTOMER` audit
  event (force-dynamic server component) — access is auditable.
- Audit log visible on the customer page (timeline section) and the
  latest events per customer in the detail view.

### 5. Repo layer
`web/src/lib/repositories/customers.ts`:
- `listCustomers(supabase, { search?, segment? })` → rows + order counts
  (+ guest-linked counts), one indexed pass like `listOrders`.
- `getCustomer360(supabase, id)` → identity + account orders + matched
  guest orders + notifications + notes + audit events.
- Pure helpers exported for tests: `digitsOf`, `matchesCustomer`
  (phone digits/email match), segment predicates.
- Notes/consent/audit writes go through Prisma (`db`) with
  `customers:write` behind the API routes.

### 6. Phases (each = one commit)
1. Schema: `User.marketingConsent`, `CustomerNote`, `CustomerAuditEvent` (both schemas + types + live db push + tracked SQL migration + RLS).
2. Repo: `listCustomers` filters/segments + `getCustomer360` + pure helpers.
3. API: notes add/remove, consent change (customers:write) with audit events.
4. UI: customer 360 page (`[id]`) + list filters/i18n + nav badge unchanged.
5. Tests: matching/segment helpers, permission matrix, note/consent audit flow (unit level).

## Acceptance mapping (#122)
- Order history + interactions in one place → §1.
- No merge on unverified identifiers → §1 (matched-but-unmerged display).
- Sensitive data restricted by role + auditable → §4 (RLS + audit events).
